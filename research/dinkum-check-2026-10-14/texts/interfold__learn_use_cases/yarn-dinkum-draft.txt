# Use Cases

This page runs ya through the jobs that suit an E3 and the limits that come with 'em. It's for
developers who want to know if the Interfold's the right fit for their application. Down the bottom,
you can stack yer job up against a working example and against the checks in [Limits to check](#limits-to-check).

## What fits an E3

An E3 suits a job that ticks these boxes:

- A few independent parties chip in inputs that have to stay private.
- The application needs the one result out of all the inputs, and that result's right to be public.
- The result's a calculation BFV handles well, say a sum, a count, or a tally.
- Nobody's happy with any single operator lookin' after the inputs.
- The application can hang about for the E3 stages. An E3 won't give ya a real-time result.

## Private voting (CRISP)

CRISP (Coercion-Resistant Impartial Selection Protocol) is the reference application in
`examples/CRISP`. It's a full, working E3 program for secret ballots.

| Part of the E3    | What CRISP does                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------- |
| Request           | The CRISP command-line tool requests one E3 for each voting round.                          |
| Inputs            | Each voter encrypts a ballot in the browser under the committee key.                        |
| Input proof       | The client generates a Noir proof that the ballot is valid. `CRISPProgram.sol` verifies it. |
| Data availability | The ciphertext bytes go to Avail. The program checks the VectorX receipt.                   |
| Secure process    | An OpenVM program adds the encrypted ballots into an encrypted tally.                       |
| Output            | The committee decrypts only the tally. Individual ballots stay encrypted.                   |

CRISP's got its own contracts, Noir circuits, a Rust coordination server, and a React client. Kick off
with the [CRISP introduction](/CRISP/introduction), then follow [Setup](/CRISP/setup) to get it runnin'.

## Sealed-bid auctions and private markets

Bidders put in encrypted bids, and only the auction result gets decrypted. That pattern lines up with
the E3 model. Where it comes unstuck is the computation. The template and CRISP only use homomorphic
addition. Anything else costs more and chews through the limited noise budget of the BFV parameter set.

Before ya build an auction, make dead sure yer secure process can work out the result inside that
budget. A design can also decrypt an aggregate, say the number of bids at each price level. The
contract can then work out the result from the aggregate. That way the aggregate's out in the open,
but the individual bids aren't.

## Aggregate statistics over private data

A handful of organisations can work out a total, a count, or a histogram over records they don't
share with each other. Each organisation encrypts its values, and the secure process adds 'em up.
Only the aggregate gets decrypted. This pattern uses the same addition as the default template,
which sums all the inputs.

## Limits to check

Have a squiz at these limits before ya design an E3 program:

- **The output is public.** The plaintext output goes on-chain. With only a few inputs, someone can
  suss out an individual value, say a tally with one vote in it. Where that matters, the program
  must enforce a minimum input count or other rules.
- **The committee is the trust boundary.** If T + 1 committee members get together on the sly, they can
  decrypt any ciphertext under the committee key. A bigger committee pushes T up. On mainnet, only
  `Small` (T = 9) can be requested at launch.
- **Inputs need validation.** The E3 program decides which inputs it'll take. Without an input proof,
  a dodgy ciphertext can stuff up the result or stop the E3 in its tracks.
- **Time matters.** Committee setup, the input window, computation, and decryption each have their own
  deadline. The [E3 lifecycle](/learn/e3-lifecycle) page lists the values.
- **Costs grow with the committee.** The fee covers the committee's work, and it goes up with N. Use
  `getE3Quote` to get the fee before ya put in a request.

## Data protection

The design can give an application a leg-up on its data-protection goals. No single operator holds a
plaintext input, and the committee only decrypts the output. But the design on its own doesn't make an
application compliant with a regulation. Sortin' out that assessment is the application owner's job.
