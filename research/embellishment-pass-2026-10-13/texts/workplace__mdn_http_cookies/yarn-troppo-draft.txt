Ever hear the one about the cookie you can't dunk in your cuppa? A **cookie** (also known as a web cookie or browser cookie) is a little scrap of data a server sends off to a user's web browser. And the browser's not fussy with 'em: it can stash cookies away, whip up new cookies, fiddle with the ones it's already got, and send them back to the same server with later requests. Cookies let web applications hang onto a limited bit of data and remember state information, and that's handy, cos left to itself the HTTP protocol is [stateless](/en-US/docs/Web/HTTP/Guides/Overview#http_is_stateless_but_not_sessionless). Memory like a goldfish, by default.

So in this article we'll run through what cookies actually get used for, the best practices for using them, and what they mean for your privacy and security, which is where it gets interesting.

## What cookies are used for

Mostly, the server has a squiz at what's in the HTTP cookies to work out whether different requests are coming from the same browser/user, and then it sends back a personalised response or a generic one, whichever fits. Here's how a basic user sign-in system plays out:

1. The user sends their sign-in credentials to the server, say through a form submission.
2. If the credentials check out, the server updates the UI to show the user's signed in, and sends back a cookie containing a session ID that records their sign-in status on the browser. Like a stamp on the back of your hand at the door.
3. A bit later, the user wanders off to a different page on the same site. The browser sends the cookie containing the session ID along with that request, basically going "Still me, still signed in, reckon."
4. The server checks the session ID and, if it's still valid, sends the user a personalised version of the new page. If it's not valid, the session ID gets binned and the user gets a generic version of the page (or maybe an "access denied" message and a polite request to sign in again).

![visual representation of the above sign-in system description](/shared-assets/images/diagrams/http/cookies/cookie-basic-example.png)

Cookies mostly earn their keep three ways:

- **Session management**: User sign-in status, what's in the shopping cart, game scores, or whatever other user session details the server needs to keep in its head.
- **Personalisation**: User preferences, like display language and UI theme.
- **Tracking**: Recording and analysing what users get up to. Yep, that's the one people worry about.

### Data storage

Back in the early days of the web, when there wasn't anything else going, cookies got used for general client-side data storage. Nowadays the modern storage APIs are the way to go, for example the [Web Storage API](/en-US/docs/Web/API/Web_Storage_API) (`localStorage` and `sessionStorage`) and [IndexedDB](/en-US/docs/Web/API/IndexedDB_API).

They're built for storage from the ground up, they never send data off to the server, and they don't come with the other headaches of using cookies for storage:

- Browsers generally cap how many cookies you can have per domain (it varies by browser, usually somewhere in the hundreds), and how big each cookie can be (usually 4KB, which is tiny). Storage APIs can hold way more data.
- Cookies get sent along with every single request, so they can drag performance down (on a slow mobile data connection out in the sticks, for example), especially if you've got heaps of cookies set.

> [!NOTE]
> If you want a look at the stored cookies (and any other storage a web page is using), you can use the [Storage Inspector](https://firefox-source-docs.mozilla.org/devtools-user/storage_inspector/index.html) in Firefox Developer Tools, or the [Application panel](https://developer.chrome.com/docs/devtools/progressive-web-apps) in Chrome Developer Tools.

## Creating, removing, and updating cookies

Once a server's got an HTTP request, it can send one or more {{HTTPHeader("Set-Cookie")}} headers back with the response, and each of those sets its own separate cookie. You set a cookie by giving it a name-value pair, simple as, like this:

```http
Set-Cookie: <cookie-name>=<cookie-value>
```

And this HTTP response tells the browser that gets it to store a pair of cookies. Choccy and strawberry, no less:

```http
HTTP/2.0 200 OK
Content-Type: text/html
Set-Cookie: yummy_cookie=chocolate
Set-Cookie: tasty_cookie=strawberry

[page content]
```
