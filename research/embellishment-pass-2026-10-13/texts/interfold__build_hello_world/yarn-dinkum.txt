# Hello World

In this tutorial you'll change the FHE computation in the default template and run the E3 again. It's meant for
developers who've already been through the [Quick Start](/build/quick-start). Once you're done, your E3 hands back 2 ×
(a + b) instead of plain a + b, and you'll know which files hold the computation, its test, and its labels
in the client.

## Before you begin

You'll want the `my-first-e3` project from the [Quick Start](/build/quick-start), just as it was, nothing changed. Every one of the
paths on this page is relative to the project folder.

## How the template computes

The whole FHE computation lives in the one Rust function, `fhe_processor`, in `program/src/lib.rs`. Everything else
in the template is just ferrying ciphertexts to this function and carting its result off to the committee.

1. The client encrypts each number with the committee public key, then calls `MyProgram.publishInput`.
2. As soon as the input window closes, the coordination server (`server/index.ts`) reads the published
   inputs and fires them off to the program server on port 13151.
3. The program server (`.interfold/support/dev/src/main.rs`) calls `fhe_processor` and sends the
   encrypted result straight back to the coordination server.
4. The coordination server publishes the encrypted result, and the committee decrypts it.

Here's what the default computation in `program/src/lib.rs` looks like. We've pulled out the doc comment above `policy`
here:

```rust filename="program/src/lib.rs"
use e3_compute_provider::{FHEProcessorInput, InputPolicy};
use fhe::bfv::Ciphertext;
use fhe_traits::{DeserializeParametrized, Serialize};

pub fn policy() -> InputPolicy {
    InputPolicy::default()
}

/// Implementation of the CiphertextProcessor function
pub fn fhe_processor(fhe_inputs: FHEProcessorInput<'_>) -> Vec<u8> {
    let mut sum = Ciphertext::zero(fhe_inputs.params);
    for (bytes, _) in fhe_inputs.ciphertexts {
        let ciphertext = Ciphertext::from_bytes(&bytes, fhe_inputs.params).unwrap();
        sum += &ciphertext;
    }

    sum.to_bytes()
}
```

- `FHEProcessorInput` has got two fields. `ciphertexts` yields `(Vec<u8>, u64)` pairs one at a time: the
  serialised ciphertext and its input index. `params` holds the BFV parameters of the E3.
- `Ciphertext::zero` makes the zero ciphertext, which is where you start from. The `+=` operator then adds each input
  ciphertext onto it. This addition is homomorphic: the function adds up the hidden values without ever getting
  a squiz at them.
- `sum.to_bytes()` serialises the encrypted result.
- `policy()` returns the input policy. The default policy just uses every published input.

<Callout type='info'>
  The template asks for E3s with the `insecure-512` parameter set. Its plaintext modulus is 100, so
  every result gets worked out modulo 100. For this tutorial, keep 2 × (a + b) under 100.
</Callout>

## Change the computation

<Steps>

### Stop the stack

If you've got `pnpm dev:all` running, hit `Ctrl+C` in its terminal.

### Double the encrypted sum

Over in `program/src/lib.rs`, swap the `fhe_processor` function out for this version:

```rust filename="program/src/lib.rs" {9-11}
/// Implementation of the CiphertextProcessor function
pub fn fhe_processor(fhe_inputs: FHEProcessorInput<'_>) -> Vec<u8> {
    let mut sum = Ciphertext::zero(fhe_inputs.params);
    for (bytes, _) in fhe_inputs.ciphertexts {
        let ciphertext = Ciphertext::from_bytes(&bytes, fhe_inputs.params).unwrap();
        sum += &ciphertext;
    }

    // Add the encrypted sum to itself. The hidden value becomes 2 × (a + b).
    let doubled = &sum + &sum;
    doubled.to_bytes()
}
```

`&sum + &sum` adds the two ciphertexts and gives you back a new ciphertext. You won't need any new imports for it.

### Update the unit test

Down the bottom of `program/src/lib.rs` there's a test that encrypts 3 and 2 and calls `fhe_processor`. Bump the
expected value from 5 to 10:

```rust filename="program/src/lib.rs"
        let tally = Vec::<u64>::try_decode(&decrypted, Encoding::poly())?;
        assert_eq!(tally[0], 10);
        Ok(())
```

### Run the unit test

```bash
cargo test -p e3-user-program
```

Cargo should print `test tests::test ... ok`. If the test fails, go back and check your `fhe_processor` against the
code in the step before.

### Update the label on the input step

In `client/src/pages/steps/EnterInputs.tsx`, track down this line:

```tsx filename="client/src/pages/steps/EnterInputs.tsx"
<strong className='font-semibold'>Ready to compute:</strong> {input1} + {input2} = ?
```

Change it to:

```tsx filename="client/src/pages/steps/EnterInputs.tsx"
<strong className='font-semibold'>Ready to compute:</strong> 2 × ({input1} + {input2}) = ?
```

### Update the label on the results step

Then in `client/src/pages/steps/Results.tsx`, track down this line:

```tsx filename="client/src/pages/steps/Results.tsx"
{
  submittedInputs
    ? `${submittedInputs.input1} + ${submittedInputs.input2} = ${result !== null ? result : '…'}`
    : '…'
}
```

Change it to:

```tsx filename="client/src/pages/steps/Results.tsx"
{
  submittedInputs
    ? `2 × (${submittedInputs.input1} + ${submittedInputs.input2}) = ${result !== null ? result : '…'}`
    : '…'
}
```

### Start the stack

```bash
pnpm dev:all
```

The `PROGRAM` process runs `interfold program start`. In dev mode that command runs
`cargo run --bin e3-support-scripts-dev`, so Cargo rebuilds the program server with your new
`fhe_processor` in it.

### Run an E3

Open [http://localhost:3000](http://localhost:3000). If the client's still showing the result of an earlier
E3, select **Start over** up in the top bar. Request an E3, then punch in 5 and 3.

On the input step you'll see `Ready to compute: 2 × (5 + 3) = ?`, and on the results step, `2 × (5 + 3) = 16`. Job done.

</Steps>

## Why nothing else changes

- **The contract.** `MyProgram.publishInput` stores a commitment for each input, and
  `MyProgram.verify` checks the compute proof. The computation isn't in either of them.
- **The coordination server.** `server/index.ts` passes every published input on to the program server
  and publishes whatever output comes back. It hasn't got a clue what the computation does.
- **The deployment.** Every time it starts, `pnpm dev:all` deploys the contracts again on a fresh local chain.

<Callout type='info'>
  In dev mode, the program server runs `fhe_processor` without a proof, and the template deploys
  `MockOpenVmReceiptVerifier`, which waves through every receipt on the local chain. Once you're on real proofs, though,
  `MyProgram.verify` checks the OpenVM receipt against the `imageId` that `MyProgram` gets when
  it's deployed. Change the program and you change that identity, so compile and deploy again. Have a geek at
  [Compute provider](/build/e3-program/compute-provider).
</Callout>

## Update the integration test

There's an end-to-end test in the template too, in `tests/integration.spec.ts`. It encrypts 1 and 2 and expects
their sum, so now you've made your change, update the expected value:

```ts filename="tests/integration.spec.ts"
expect(BigInt(result)).toBe(2n * (num1 + num2))
```

Run the test with `pnpm test:integration`. Heads up: this test needs a CLI that's built with the
`test-only-skip-proof-aggregation` Cargo feature, and the release binaries don't come with it. Check out
[Installation](/build/installation#install-the-cli) for a source build.

## Operations on ciphertexts

The template uses the `fhe` crate from `gnosisguild/fhe.rs` at tag `v0.4.2`. For a `Ciphertext`,
here's the operators that crate implements:

| Operation                   | Operator             | Example           |
| --------------------------- | -------------------- | ----------------- |
| Add two ciphertexts         | `+`, `+=`            | `&a + &b`         |
| Subtract two ciphertexts    | `-`, `-=`            | `&a - &b`         |
| Negate a ciphertext         | unary `-`            | `-&a`             |
| Add or subtract a plaintext | `+`, `+=`, `-`, `-=` | `&a + &plaintext` |
| Multiply by a plaintext     | `*`, `*=`            | `&a * &plaintext` |

A `Plaintext` has to use the very same parameters object as the ciphertext, that's `fhe_inputs.params`. If
the parameters objects don't match, the operator panics.

Every result wraps modulo the plaintext modulus. So a negative result, say from `&a - &b` with
`a < b`, wraps round to a big value. The crate implements `*` for two ciphertexts as well, but the default
template doesn't use it, and we won't go into it on this page.
