## Introduction

GitHub flow is a lightweight, branch-based workflow. The GitHub flow's handy for every man and his dog, not just developers. For instance, here at GitHub, we use GitHub flow for our [site policy](https://github.com/github/site-policy), [documentation](https://github.com/github/docs), and [roadmap](https://github.com/github/roadmap).

## Prerequisites

To follow GitHub flow, you'll need a GitHub account and a repository. For the drum on how to set up an account, see [Creating an account on GitHub](/en/account-and-profile/how-tos/account-management/creating-an-account-on-github). For how to create a repository, have a squiz at [Quickstart for repositories](/en/repositories/creating-and-managing-repositories/quickstart-for-repositories). And for how to track down an existing repository to chip in on, see [Finding ways to contribute to open source on GitHub](/en/get-started/exploring-projects-on-github/finding-ways-to-contribute-to-open-source-on-github).

## Following GitHub flow

> \[!TIP]
> You can get through every step of GitHub flow in the GitHub web interface, the command line and [GitHub CLI](https://cli.github.com), or [GitHub Desktop](/en/desktop). For more on the tools you can use to hook up to GitHub, see [Connecting to GitHub](/en/get-started/using-github/connecting-to-github).

### Create a branch

Create a branch in yer repository. A short branch name that says what it's for lets yer collaborators see what's on the go at a glance. For example, `increase-test-timeout` or `add-code-of-conduct`. For more on that, see [Managing branches within your repository](/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository).

When ya create a branch, ya get a space to work in without mucking up the default branch. On top of that, ya give collaborators a chance to review yer work.

### Make changes

On yer branch, make whatever changes ya like to the repository. For more on that, see [Creating new files](/en/repositories/working-with-files/managing-files/creating-new-files), [Editing files](/en/repositories/working-with-files/managing-files/editing-files), [Renaming a file](/en/repositories/working-with-files/managing-files/renaming-a-file), [Moving a file to a new location](/en/repositories/working-with-files/managing-files/moving-a-file-to-a-new-location), or [Deleting files in a repository](/en/repositories/working-with-files/managing-files/deleting-files-in-a-repository).

Yer branch is a safe spot to make changes. If ya stuff up, ya can revert yer changes or push more changes to fix the stuff-up. Yer changes won't land on the default branch till ya merge yer branch.

Commit and push yer changes to yer branch. Give each commit a message that says what it does, so you and whoever comes along later can work out what changes the commit's got in it. For example, `fix typo` or `increase rate limit`.

Ideally, each commit holds one self-contained, complete change. That makes it dead easy to revert yer changes if ya decide to go a different way. Say you're keen to rename a variable and add some tests: put the variable rename in one commit and the tests in another commit. Later on, if ya want to keep the tests but revert the variable rename, ya can revert just the commit that had the variable rename in it. If ya put the variable rename and the tests in the same commit, or spread the variable rename over a heap of commits, you'd be flat out for heaps longer revertin' yer changes.

When ya commit and push yer changes, ya back up yer work to remote storage. That means ya can get at yer work from any device. It also means yer collaborators can see yer work, answer questions, and chuck in suggestions or contributions.

Keep on makin', committin', and pushin' changes to yer branch till you're ready to ask for feedback.
