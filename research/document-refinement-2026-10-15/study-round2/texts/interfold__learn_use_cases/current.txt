# Use Cases

This page runs through the tasks an E3 can handle and the limits you'll need to work within. It's for developers
working out whether the Interfold fits their application. By the end, you can weigh up your task against a
working example and the checks in [Limits to check](#limits-to-check).

## What fits an E3

An E3 fits the bill when your task has all these properties:

- Several independent parties put in inputs that must stay private.
- The application needs a single result from all the inputs, and that result can be public.
- The result comes from a computation BFV handles well, such as a sum, a count, or a tally.
- There's no single operator you can accept as custodian of the inputs.
- The application can wait through the E3 stages. An E3 won't give you a real-time result.

## Private voting (CRISP)

CRISP (Coercion-Resistant Impartial Selection Protocol), in
`examples/CRISP`, is the reference application: a complete E3 program for secret ballots that works from start to finish.

| Part of the E3    | What CRISP does                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------- |
| Request           | The CRISP command-line tool requests one E3 for each voting round.                          |
| Inputs            | Each voter encrypts a ballot in the browser under the committee key.                        |
| Input proof       | The client generates a Noir proof that the ballot is valid. `CRISPProgram.sol` verifies it. |
| Data availability | The ciphertext bytes go to Avail. The program checks the VectorX receipt.                   |
| Secure process    | An OpenVM program adds the encrypted ballots into an encrypted tally.                       |
| Output            | The committee decrypts only the tally. Individual ballots stay encrypted.                   |

CRISP comes with its own contracts, Noir circuits, a Rust coordination server, and a React client. Start
with the [CRISP introduction](/CRISP/introduction), then work through [Setup](/CRISP/setup) to run it.

## Sealed-bid auctions and private markets

Bidders put in encrypted bids, and only the auction result gets decrypted. That fits the E3
model. What you can compute is the limit. The template and CRISP stick to homomorphic addition. Other
operations cost more and eat into the BFV parameter set's limited noise budget.

Before you get stuck into building an auction, check that your secure process can compute the result within that
budget. Another design is to decrypt an aggregate, such as the number of bids at each price level.
The contract can then work out the result from that aggregate. This reveals the aggregate, but
keeps the individual bids private.

## Aggregate statistics over private data

Several organisations can work out a total, a count, or a histogram over records without sharing those
records. Each organisation encrypts its values, and the secure process adds them together. Only the aggregate
gets decrypted. It's the same addition used by the default template, which sums all inputs.

## Limits to check

Check these limits before you get into designing an E3 program:

- **The output is public.** The plaintext output goes on-chain. With only a few inputs, an individual
  value can show through: a tally with one vote, for instance. Where this matters, the program must enforce a minimum input
  count or other rules.
- **The committee is the trust boundary.** If T + 1 committee members collude, they can decrypt any
  ciphertext under the committee key. A bigger committee raises T. At mainnet launch, you can request only `Small` (T = 9).
- **Inputs need validation.** The E3 program chooses which inputs to accept. Without an input proof,
  a malformed ciphertext can corrupt the result or bring the E3 to a stop.
- **Time matters.** Committee setup, the input window, computation, and decryption each have their own
  deadline. You'll find the values on the [E3 lifecycle](/learn/e3-lifecycle) page.
- **Costs grow with the committee.** The fee covers the committee's work and goes up with N. Use
  `getE3Quote` to find out the fee before putting in your request.

## Data protection

The design can help an application meet its data-protection goals. No single operator holds a plaintext
input, and the committee decrypts only the output. The design on its own doesn't make an application
compliant with a regulation. Assessing that is the application owner's responsibility.
