# Use Cases

This page runs through the tasks that suit an E3 and the limits that come with them. It's for developers
keen to know whether the Interfold suits their application. At the end, you can stack your task up against a
working example and the checks in [Limits to check](#limits-to-check).

## What fits an E3

An E3 suits a task that ticks these boxes:

- Several independent parties chip in inputs that must stay private.
- The application needs one result from all the inputs, and that result can be public.
- The result is a computation BFV handles well, like a sum, a count or a tally.
- No single operator can be trusted to mind the inputs.
- The application can wait out the E3 stages. An E3 doesn't give you a result in real time.

## Private voting (CRISP)

CRISP (Coercion-Resistant Impartial Selection Protocol) is the reference application in
`examples/CRISP`. It's a complete, working E3 program for secret ballots.

| Part of the E3    | What CRISP does                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------- |
| Request           | The CRISP command-line tool requests one E3 for each voting round.                          |
| Inputs            | Each voter encrypts a ballot in the browser under the committee key.                        |
| Input proof       | The client generates a Noir proof that the ballot is valid. `CRISPProgram.sol` verifies it. |
| Data availability | The ciphertext bytes go to Avail. The program checks the VectorX receipt.                   |
| Secure process    | An OpenVM program adds the encrypted ballots into an encrypted tally.                       |
| Output            | The committee decrypts only the tally. Individual ballots stay encrypted.                   |

CRISP comes with its own contracts, Noir circuits, a Rust coordination server and a React client. Kick off
with the [CRISP introduction](/CRISP/introduction), then work through [Setup](/CRISP/setup) to get it running.

## Sealed-bid auctions and private markets

Bidders put in encrypted bids, and only the auction result gets decrypted. That pattern lines up with the E3
model. The catch is the computation. The template and CRISP only use homomorphic addition. Anything else
costs more and eats into the limited noise budget of the BFV parameter set.

Before you build an auction, make sure your secure process can work out the result within that
budget. A design can also decrypt an aggregate instead, like the number of bids at each price level.
The contract can then work out the result from the aggregate. That design gives away the aggregate, but
not the individual bids.

## Aggregate statistics over private data

Several organisations can work out a total, a count or a histogram over records they don't
share with each other. Each organisation encrypts its values, and the secure process adds them up. Only the aggregate
gets decrypted. This pattern uses the same addition as the default template, which sums all the inputs.

## Limits to check

Run through these limits before you design an E3 program:

- **The output is public.** The plaintext output goes on-chain. A handful of inputs can give away
  an individual value, like a tally with one vote in it. The program must enforce a minimum input
  count or other rules where that matters.
- **The committee is the trust boundary.** T + 1 committee members who get in cahoots can decrypt any
  ciphertext under the committee key. A bigger committee raises T. On mainnet, only `Small` (T = 9)
  can be requested at launch.
- **Inputs need validation.** The E3 program decides which inputs to take. Without an input proof,
  a malformed ciphertext can stuff up the result or stop the E3 dead.
- **Time matters.** Committee setup, the input window, computation and decryption each have a
  deadline. The [E3 lifecycle](/learn/e3-lifecycle) page lists the values.
- **Costs grow with the committee.** The fee covers the committee's work, and it goes up with N. Use
  `getE3Quote` to get the fee before you put in a request.

## Data protection

The design can help an application meet data-protection goals. No single operator holds a plaintext
input, and the committee only decrypts the output. The design doesn't, on its own, make an application
compliant with a regulation. That assessment is up to the application owner.
