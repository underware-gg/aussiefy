## Introduction

Okay, so. GitHub flow's a light-as-a-feather way of workin' that's all built round branches. And it's not just for the coders, either: every man and his dog can get some use out of it. Here at GitHub, for instance, we run GitHub flow on our own [site policy](https://github.com/github/site-policy), [documentation](https://github.com/github/docs), and [roadmap](https://github.com/github/roadmap).

## Prerequisites

To have a go at GitHub flow you'll need two things: a GitHub account and a repository. Haven't got an account? Have a look at [Creating an account on GitHub](/en/account-and-profile/how-tos/account-management/creating-an-account-on-github). No repo yet? [Quickstart for repositories](/en/repositories/creating-and-managing-repositories/quickstart-for-repositories) will sort ya out. And if you're after a repo someone else has already got goin' that ya can pitch in on, check out [Finding ways to contribute to open source on GitHub](/en/get-started/exploring-projects-on-github/finding-ways-to-contribute-to-open-source-on-github).

## Following GitHub flow

> \[!TIP]
> Ya can do every step of GitHub flow through the GitHub website, from the command line and the [GitHub CLI](https://cli.github.com), or with [GitHub Desktop](/en/desktop). Whatever floats ya boat. For the full rundown on the tools ya can hook up to GitHub with, see [Connecting to GitHub](/en/get-started/using-github/connecting-to-github).

### Create a branch

First up, make a branch in your repository. Give it a short name that says what it's for, so your offsiders can have a quick squiz and know what's on the go without diggin' through the lot. Somethin' like `increase-test-timeout` or `add-code-of-conduct`. For more on that, see [Managing branches within your repository](/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository).

A brand-spankin'-new branch gives ya your own little paddock to work in without muckin' up the default branch. On top of that, it gives your teammates a chance to run their eye over what you've done.

### Make changes

On your branch, make whatever changes ya like to the repository. For the how-to, see [Creating new files](/en/repositories/working-with-files/managing-files/creating-new-files), [Editing files](/en/repositories/working-with-files/managing-files/editing-files), [Renaming a file](/en/repositories/working-with-files/managing-files/renaming-a-file), [Moving a file to a new location](/en/repositories/working-with-files/managing-files/moving-a-file-to-a-new-location), or [Deleting files in a repository](/en/repositories/working-with-files/managing-files/deleting-files-in-a-repository).

Your branch is a safe spot to have a crack. Stuff somethin' up? No worries: ya can roll your changes back, or push a few more to fix the blue. None of it lands on the default branch till ya merge your branch.

Commit your changes and push 'em up to your branch. Give every commit a message that says what's in it, so you and whoever comes along after ya can work out what each commit actually did. Somethin' like `fix typo` or `increase rate limit`. Not "stuff" or "asdf", ya mug.

Best case, each commit's one change, done and dusted, on its own. That way it's dead easy to roll back if ya decide to go about it a different way. Say ya want to rename a variable and add a few tests: put the rename in one commit and the tests in another. Down the track, if ya want to keep the tests but ditch the rename, ya just roll back the one commit with the rename in it. Chuck the rename and the tests in the same commit, or smear the rename over a heap of commits, and you'll be workin' a bloody sight harder to undo it.

Committin' and pushin' your changes backs your work up to remote storage, so ya can get at it from any device. It also means your teammates can see what you're up to, answer your questions, and throw in suggestions or a bit of work of their own.

Keep makin', committin' and pushin' changes to your branch till you're ready for someone to tell ya what they reckon.
