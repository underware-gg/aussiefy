# Use Cases

Strewth, where do I start? This page runs through the sort of yakka an E3 is cut out for, and the limits that come with it. It's for developers who want to know if the Interfold's the right fit for their application. Down the bottom, ya can hold your job up against a working example and against the checks in [Limits to check](#limits-to-check), and see how it stacks up.

## What fits an E3

An E3 suits a job that ticks these boxes:

- A few separate parties each chip in inputs that have to stay private.
- The application needs one result out of all the inputs, and it's fine for that result to be public.
- The result is a sum BFV handles well: say a total, a count or a tally.
- Nobody's happy with any one operator holdin' the inputs.
- The application can sit tight while the E3 works through its stages. An E3 won't give ya a result in real time, so don't hold your breath.

## Private voting (CRISP)

CRISP (Coercion-Resistant Impartial Selection Protocol) is the reference application, and it lives in
`examples/CRISP`. It's a complete E3 program for secret ballots, and it works, start to finish.

| Part of the E3    | What CRISP does                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------- |
| Request           | The CRISP command-line tool requests one E3 for each voting round.                          |
| Inputs            | Each voter encrypts a ballot in the browser under the committee key.                        |
| Input proof       | The client generates a Noir proof that the ballot is valid. `CRISPProgram.sol` verifies it. |
| Data availability | The ciphertext bytes go to Avail. The program checks the VectorX receipt.                   |
| Secure process    | An OpenVM program adds the encrypted ballots into an encrypted tally.                       |
| Output            | The committee decrypts only the tally. Individual ballots stay encrypted.                   |

CRISP comes with the whole kit: its own contracts, Noir circuits, a Rust coordination server and a React client. Kick off
with the [CRISP introduction](/CRISP/introduction), then follow [Setup](/CRISP/setup) to get it runnin'.

## Sealed-bid auctions and private markets

Bidders put in encrypted bids, and only the result of the auction gets decrypted. That's right up the E3's alley. The catch is the maths. The template and CRISP only use homomorphic addition. Anything else costs ya more, and it eats into the BFV parameter set's noise budget, which isn't bottomless.

So before ya knock together an auction, make dead sure your secure process can work out the result inside that budget. A design can also decrypt a bunch of totals instead, say the number of bids at each price. The contract can then work out the result from those. That way the totals are out in the open, but the individual bids stay under wraps.

## Aggregate statistics over private data

A bunch of organisations can work out a total, a count or a histogram over records they don't share with each other. Each organisation encrypts its own numbers, and the secure process adds 'em up. Only the total gets decrypted, and nobody gets a squiz at anyone else's books. This pattern uses the same addition as the default template, which just adds up all the inputs.

## Limits to check

Run your eye over these limits before ya design an E3 program:

- **The output is public.** The plaintext output goes on-chain for all to see. With only a handful of inputs it can give away one person's value, like a tally with just the one vote in it. Where that matters, the program has to insist on a minimum number of inputs, or some other rules.
- **The committee is the trust boundary.** If T + 1 committee members get together and collude, they can decrypt any ciphertext under the committee key. A bigger committee pushes T up. On mainnet, only `Small` (T = 9) can be requested at launch.
- **Inputs need validation.** The E3 program decides which inputs it'll take. Without an input proof, one dodgy ciphertext can stuff up the result or bring the whole E3 to a grinding halt.
- **Time matters.** Committee setup, the input window, the computation and the decryption each have a deadline. The [E3 lifecycle](/learn/e3-lifecycle) page has the numbers.
- **Costs grow with the committee.** The fee pays for the committee's work, and it goes up with N. Use `getE3Quote` to find out what it'll set ya back before ya request.

## Data protection

The design can give an application a leg-up with its data-protection goals. No one operator ever holds a plaintext input, and the committee only decrypts the output. But the design on its own won't make an application tick the boxes for any regulation. That call's up to whoever owns the application.
